# T4.2 — Step 2 (Load): Idempotency Check

**Phase:** 4 — Load
**Depends on:** T4.1 (`load_employee` implemented)
**Required by:** T6.4 (integration test)

---

## Goal

Confirm that calling `load_employee` more than once for the same `employee_id` produces a clean replacement with no stale rows, no duplicates, and the correct final row count. This task adds no new application code — it is purely a test suite that exercises the behaviour guaranteed by T4.1's DELETE-then-INSERT pattern.

---

## Package Structure

```
tests/
  test_load_idempotency.py   ← all idempotency and edge-case tests
```

The existing `tests/test_load.py` (T4.1) covers atomicity and column mapping. This file covers re-run correctness and edge cases.

---

## Data Flow

```
First call:  load_employee(eid, chunks_A)  → N rows
Second call: load_employee(eid, chunks_B)  → M rows  (M ≠ N in the non-trivial case)
                                           ↓
skills_search_index for eid: exactly M rows, matching chunks_B
No row from chunks_A remains.
```

---

## Test Scenarios

### Scenario 1 — Basic re-index replaces rows

1. Build `chunks_A`: 3 `ChunkRecord` objects for `employee_id = 1`.
2. `load_employee(1, chunks_A)` → assert 3 rows in DB.
3. Build `chunks_B`: 5 different `ChunkRecord` objects for the same `employee_id = 1`.
4. `load_employee(1, chunks_B)` → assert exactly 5 rows in DB.
5. Assert no row from `chunks_A` is present (verify by `chunk_text` or `chunk_index`).

### Scenario 2 — Row count is always the second call's count, never the sum

After both calls the DB must contain `len(chunks_B)` rows — not `len(chunks_A) + len(chunks_B)`. This rules out any INSERT-without-DELETE path.

### Scenario 3 — No `(employee_id, field_type, chunk_index)` duplicates

After the second call, query:

```sql
SELECT employee_id, field_type, chunk_index, COUNT(*)
FROM skills_search_index
WHERE employee_id = %s
GROUP BY employee_id, field_type, chunk_index
HAVING COUNT(*) > 1
```

Assert the result is empty.

### Scenario 4 — Empty second call produces zero rows

1. `load_employee(2, chunks_C)` with 4 chunks.
2. `load_employee(2, [])` (empty list).
3. Assert 0 rows for `employee_id = 2` — not 4.

### Scenario 5 — Multiple employees are isolated

1. `load_employee(10, chunks_for_10)` — 3 rows for employee 10.
2. `load_employee(11, chunks_for_11)` — 2 rows for employee 11.
3. `load_employee(10, new_chunks_for_10)` — 1 row for employee 10.
4. Assert employee 10 has exactly 1 row.
5. Assert employee 11 still has exactly 2 rows (other employees are unaffected).

### Scenario 6 — Calling with identical chunks twice is a no-op

1. `load_employee(3, chunks_D)`.
2. `load_employee(3, chunks_D)` (same object list).
3. Assert exactly `len(chunks_D)` rows — same content, no duplication.

## Fixture Design

### `make_chunk(employee_id, chunk_index, field_type, *, text, embedding)`

A factory helper that produces a fully populated `ChunkRecord` with a synthetic 384-dim L2-normalised embedding. Keeps test bodies compact.

```python
def make_chunk(employee_id, chunk_index, field_type="cv", *, text="sample text"):
    vec = [0.0] * 384
    vec[chunk_index % 384] = 1.0   # deterministic unit vector per chunk_index
    return ChunkRecord(
        employee_id=employee_id,
        field_type=field_type,
        chunk_text=text,
        chunk_index=chunk_index,
        char_start=0,
        char_end=len(text),
        token_count=len(text.split()),
        preprocess_version=str(PREPROCESS_VERSION),
        embedding=vec,
        metadata={},
    )
```

### DB cleanup

Each test is wrapped in a fixture that deletes all rows for the test `employee_id`(s) via `load_employee(eid, [])` (or a direct DELETE) in its teardown, so tests never depend on prior state.

## Contract Assertions Summary

| Assertion | SQL / check |
|---|---|
| Exact row count after second call | `SELECT COUNT(*) … WHERE employee_id = %s` |
| No stale rows from first call | `SELECT COUNT(*) … WHERE chunk_text = ANY(%s)` using first-call texts |
| No duplicates | `GROUP BY … HAVING COUNT(*) > 1` returns 0 rows |
| Isolation: other employees untouched | `COUNT(*) WHERE employee_id = other_eid` unchanged |
| Empty second call = 0 rows | `COUNT(*) … WHERE employee_id = %s` = 0 |

All tests are marked `@pytest.mark.integration` and require a live vector DB.

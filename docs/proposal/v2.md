## 1. PURPOSE & CONTEXT

OWT is a software company with around 60 employees. When staffing a new project, admins currently have no efficient way to find the right people. They rely on memory or manually browsing profiles. This feature solves that: a single search lets the admin find employees whose skills and experience match the project's requirements in seconds, not hours.

---

## 2. OBJECTIVE

Build a skills search feature that allows admins to find employees whose skills match a project's requirements.

The feature is delivered as a single unified search endpoint that supports two complementary modes, usable independently or together:

- **Semantic (free-text) search** — vector similarity search over employee CVs, experience records, and training logs. This is RAG minus the Generation step: retrieve and rank, not generate. Admin can type a natural language query like `"React developer with e-commerce experience"` and get ranked results.
- **Structured filter search** — fast SQL queries over skill/proficiency tables. Admin can filter by skill, proficiency level, position, experience, and training records.

When both modes are used together, structured filters run first to narrow candidates, then semantic search reranks the survivors.

---

## 3. TECHNOLOGY DECISIONS

### 3.1 Vector Database: pgvector

The project already uses PostgreSQL. pgvector is a PostgreSQL extension — no additional infrastructure, no extra service to deploy or maintain.

Exact cosine similarity (no approximate index needed at 60 employees).

Alternatives considered and ruled out: Qdrant, Weaviate, Milvus, Chroma, LanceDB, Elasticsearch, Typesense — all require a separate service.

### 3.2 Embedding Model: all-MiniLM-L6-v2

- 384-dimension vectors
- Runs on CPU (no GPU required)
- Well-tested for semantic similarity tasks
- Hard token limit: 256 tokens (`max_seq_length`; model truncates beyond this). Chunking targets 150 tokens with 20–25% overlap.
- Can be swapped for a better model later without changing architecture.

### 3.3 Embedding Runtime: Python FastAPI service

The skills-search module is built entirely in Python/FastAPI. The embedding service runs as a sub-module of the same FastAPI application, not as a separate sidecar.

**Library choice: onnxruntime over sentence_transformers:**

- `sentence_transformers` pulls in PyTorch (~1.5 GB) as a dependency — disproportionate for CPU-only inference on a small dataset in a production internal app.
- Use `onnxruntime` + the ONNX export of all-MiniLM-L6-v2 instead (~50 MB) — lighter, faster cold start, no PyTorch in production.
- Trade-off: `onnxruntime` requires manually handling tokenization, padding, attention masks, and mean pooling. If implementation complexity becomes a blocker, `sentence_transformers` is the fallback; the rest of the architecture is unaffected.

**Security:** The `/embed` endpoint is internal — called only by the FastAPI search module. It must be protected with a shared secret header (`X-Internal-Token`) and bound to localhost or an internal network interface only.

## 4. INDEX TABLE DESIGN

```sql
CREATE EXTENSION IF NOT EXISTS vector;

-- Naming note: table is 'users' (not 'employees') — confirmed from entity
-- decorators and migrations. Column name employee_id follows existing
-- convention used in timesheets table (employee_id FK → users.id).
--
-- field_type values match actual table names in this codebase:
--   'training'   → trainings table
--   'experience' → experiences table
--   'task'       → task_assignments table (short alias)
--   'cv'         → cv_overview.introduction in users module
--   'skill'      → skills table (for free-text → skill expansion)

CREATE TABLE skills_search_index (
  id                 SERIAL PRIMARY KEY,
  employee_id        INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  field_type         TEXT NOT NULL
                     CHECK (field_type IN ('cv', 'experience', 'training', 'task', 'skill')),
  chunk_index        INT NOT NULL DEFAULT 0,
  -- Sequence number across all chunks of this (employee_id, field_type).
  -- Assigned globally when all sources of a type are re-indexed together.
  chunk_text         TEXT NOT NULL,
  -- Natural-language prose. Never embed JSON here — the model was trained
  -- on prose; JSON syntax wastes 30–40% of the token budget on noise.
  embedding          VECTOR(384) NOT NULL,
  metadata           JSONB NOT NULL DEFAULT '{}',
  -- Structured data for filtering, boosting, and display. See below.
  preprocess_version SMALLINT NOT NULL DEFAULT 1,
  -- Tracks which preprocessing rules produced this chunk. Bump when rules
  -- change and schedule a rebuild via PUT /admin/skills-search/rebuild.
  updated_at         TIMESTAMP DEFAULT NOW(),

  UNIQUE (employee_id, field_type, chunk_index)
);
```

### Metadata JSONB schema

`chunk_text` carries natural-language prose for embedding quality. `metadata` carries structured facts for filtering, boosting, and result card display. Never put structured facts inside `chunk_text`.

The schema has two layers:

**Fixed fields** — present in every row regardless of `field_type`. These are the fields used for cross-type filtering, sorting, and display logic.

| Field | Type | Description |
|---|---|---|
| `skills` | `string[]` | Skill names referenced in this chunk. Empty array `[]` if none. |
| `date_from` | `string \| null` | Start date in `YYYY-MM` format. Null if not applicable. |
| `date_to` | `string \| null` | End date in `YYYY-MM` format. Null if ongoing or not applicable. |

**Type-specific additional fields** — layered on top of the fixed fields. These vary by `field_type` and are used for richer display and type-scoped filtering.

| `field_type` | Additional fields |
|---|---|
| `experience` | `"project"` (string), `"domain"` (string), `"years"` (int) |
| `training` | `"title"` (string), `"topic"` (string), `"level"` (string) |
| `task` | `"title"` (string) |

### Chunking strategy

Use token-aware, semantic-preserving chunks of **100–200 tokens** with a **sliding-window overlap of 20–30%**, keeping chunk boundaries aligned to sentences or logical sections. This balances the capacity and accuracy of `all-MiniLM-L6-v2` while preserving context for retrieval.

**Why this works:**
- `all-MiniLM-L6-v2` maps sentences/paragraphs to 384-dim vectors and performs best when chunks contain coherent semantic units rather than arbitrary cut points — sentence/paragraph alignment reduces noisy embeddings.
- The model's `max_seq_length` is 256 tokens, so 100–200 token chunks give a good trade-off between semantic completeness and index granularity while staying well within the limit.

**Recommended defaults:**
- Chunk target: **150 tokens**
- Overlap: **20–25% of chunk size** (30–38 tokens)
- Boundary rule: prefer sentence/paragraph boundaries; fall back to token split only if necessary

**Workflow (starting at Normalize):**

1. **Normalize text** — Clean whitespace, remove repeated line breaks, unify punctuation and encoding, strip boilerplate (headers/footers) where identifiable. Output: cleaned plain text.

2. **Structure analysis** — Detect headings, paragraphs, lists, tables, code fences by regex/heuristics; tag blocks with type and position. Output: ordered list of structured blocks (type, text, char range).

3. **Tokenize & sentence-split** — Use your chosen tokenizer to get token counts and a sentence splitter (or tokenizer that provides sentence boundaries). Output: sequence of sentences with token counts and block references.

4. **Chunk builder (primary pass)** — Target tokens per chunk: default 150 (recommended range 100–200). Accumulate full sentences until adding the next would exceed target; prefer stopping at sentence boundaries. Emit chunk text and metadata (`doc_id`, `block_type`, `section_title`, `chunk_index`, `token_count`, `char_start`, `char_end`).

5. **Sliding-window overlap** — Apply overlap of 20–30% (default 25%). Implement by retaining the last N tokens or last M sentences from previous chunk as the start of the next chunk.

6. **Special-block handling** — For very large blocks, recursively split at paragraph → sentence → token level until within limits.

7. **Optional semantic refine** — Compute embeddings for chunks (or sentences), cluster to detect topic shifts, then merge/split chunks to maximize topical coherence. Use only if structure is noisy.

8. **Metadata & provenance** — Save `chunk_id`, `chunk_index`, `token_count`, `char_range`, `created_at`.

9. **Embed & index** — Encode chunk text with `all-MiniLM-L6-v2` (or your chosen model), store vector in vector DB, link to metadata in database.

10. **Monitor & iterate** — Log chunk-size distribution, retrieval precision, and downstream LLM performance; adjust target size/overlap and semantic refine if needed.

**Parameter defaults (start here and tune):**
- Target tokens: **150**
- Overlap ratio: **0.25 (25%)**
- Boundary rule: prefer sentence/paragraph; allow token-level only when necessary
- Special types: tables/code stored separately

### Query vectorization strategy

Converting a free-text question into one or more normalized, semantically-rich query vectors.

#### Lightweight normalize-then-embed pipeline (lower latency)

Use this when queries are short and explicit, structured skill fields provide exact-match coverage, and you prioritize simplicity and speed.

**When skipping full parsing is reasonable:**
- Queries are short and clearly name skills (`"Who has Java or NodeJs?"`).
- Structured skill fields exist and exact-tag boosting compensates for noisy semantic matches.
- You need fewer pipeline steps and faster response times.

**Minimal pipeline:**

1. **Normalize text** — lowercase, trim, clean whitespace (same as Section 5.7).
2. **Alias map + boolean split** — run a small alias normalization pass (`"node"`, `"node.js"` → `"nodejs"`), then split on `" or "`, `" and "`, commas to get per-skill tokens.
3. **Build 1–3 query strings:**
   - `full_query` = the full normalized sentence
   - `per_skill_queries` = each token/group after alias normalization and split
4. **Embed** `full_query` and each `per_skill_query` (reuse cached vectors for repeated terms).
5. **Search and combine:**
   - OR detected → union results, rank by max similarity, boost exact skill-tag matches.
   - AND detected → intersect or require multiple hits, rank by combined similarity.
6. **Post-filter/boost** with exact skill tags from the DB and return results with provenance flags.

**Recommended**
- **Controlled vocabulary + exact-tag boost:** always combine semantic results with an exact-match lookup on canonical skill fields. This is the primary safety net.
- **Lightweight alias normalization:** map obvious variants before embedding to prevent most misses cheaply.
- **Heuristic boolean detection:** when `" and "`, `" or "`, or `" not "` are present, split into per-skill query strings to approximate boolean logic without full parsing.
- **Logging + fallback:** if top-N results have low similarity scores, fall back to structured keyword search and return both sets with provenance flags.

#### Worked example — "Who have Java and NodeJS skills?" (operator = AND)

Concrete output at each step of the minimal pipeline.

**Step 1 — Raw input**

```
"Who have Java and NodeJS skills?"
```

**Step 2 — Normalize text**

Lowercase, trim, collapse whitespace, remove stray punctuation:

```
"who have java and nodejs skills"
```

**Step 3 — Alias map + boolean split (heuristic boolean detection)**

- Alias normalization: `"node"`, `"node.js"` → `"nodejs"` (no change needed here).
- Detect boolean connectors: sentence contains `" and "` → operator = `AND`.
- Split on `" and "`, commas, `" or "`:

```
per_skill_tokens : ["java", "nodejs"]
full_query       : "who have java and nodejs skills"
```

**Step 4 — Build query strings to embed**

```
full_query        : "who have java and nodejs skills"
per_skill_queries : ["java", "nodejs"]
cached_vector_keys: ["java", "nodejs"]
```

**Step 5 — Embedding**

(Real vectors are 384-dim floats; short illustrative values shown.)

```
embed(full_query) → full_vec    ≈ [0.12, -0.03, 0.45, ...]
embed("java")     → java_vec   ≈ [0.21,  0.01, 0.33, ...]
embed("nodejs")   → nodejs_vec ≈ [0.09, -0.07, 0.51, ...]
```

**Step 6 — Semantic search results** (top candidates, before tag-boosting)

| Candidate | sim(java_vec) | sim(nodejs_vec) | sim(full_vec) |
|---|---|---|---|
| Alice Nguyen | 0.78 | 0.74 | 0.76 |
| Ben Tran | 0.81 | 0.12 | 0.45 |
| Carla Le | 0.15 | 0.80 | 0.43 |
| David Ho | 0.55 | 0.58 | 0.57 |

**Step 7 — Exact-tag lookup** (canonical skill fields in DB)

```
Alice Nguyen : ["java", "nodejs"]            ← exact match on both
Ben Tran     : ["java"]
Carla Le     : ["nodejs"]
David Ho     : ["java", "nodejs (junior)"]   ← partial/variant tag
```

**Step 8 — Combine for operator = AND (intersection + ranking)**

*Step A* — require semantic score ≥ 0.5 for **both** per-skill queries:

- Alice: java 0.78 ✓ and nodejs 0.74 ✓ → passes
- David: java 0.55 ✓ and nodejs 0.58 ✓ → passes
- Ben (nodejs 0.12) and Carla (java 0.15) → fail AND threshold

*Step B* — exact-tag boost:

- Alice: exact tags for both → strong boost
- David: partial/variant nodejs tag → mild boost

Ranked intersection:

| Rank | Candidate | final_score | Reason |
|---|---|---|---|
| 1 | Alice Nguyen | 0.95 | semantic high + exact tags |
| 2 | David Ho | 0.70 | semantic mid + partial tag |

**Step 9 — Provenance flags**

```
Alice Nguyen → provenance: ["semantic (java, nodejs)", "exact-tag (java, nodejs)"]
David Ho     → provenance: ["semantic (java, nodejs)", "exact-tag (java, nodejs (junior))"]
```

Semantic scores were high (> 0.5), so structured-keyword fallback was not needed. If scores had been low (< 0.4), both semantic and tag-only results would be returned with `fallback_used: true`.

**Step 10 — Final response**

```
1. Alice Nguyen  — skills: Java, NodeJS           — evidence: semantic + exact-tag  (score 0.95)
2. David Ho      — skills: Java, NodeJS (junior)  — evidence: semantic + partial tag (score 0.70)
```

**Pipeline summary:**

```
input → normalize → per-skill queries ["java","nodejs"] → embed →
semantic search → intersect by AND (threshold 0.5) →
boost with exact tags → return ranked results with provenance
```

### Indexing upsert semantics

When any source row of a given type (experience, training, task, CV) is created, updated, or deleted:

1. **DELETE** all `skills_search_index` rows for `(employee_id, field_type)`.
2. Re-chunk all remaining source rows of that type for the employee.
3. **INSERT** the new chunk rows, assigning `chunk_index` = 0, 1, … sequentially across all chunks.
4. Wrap steps 1–3 in a transaction.

This re-indexes the full type slice for the employee on any change. At 60 employees with a small number of rows per type, this is fast and avoids needing a row-level reference to identify stale chunks.

Hooks also cover hard deletes: `@AfterRemove` on each source entity triggers the same delete-then-reindex for `(employee_id, field_type)`.

### Index refresh

A schedule to select candidates where last_indexed_at IS NULL OR last_indexed_at < updated_at

Compute embeddings, upsert vectors, and update last_indexed_at (and optional embed_checksum and model_version).

### Deactivated employees

When a user is set to `is_active = false`, their index rows are NOT deleted. All search queries filter by `users.is_active = true` at query time. This avoids unnecessary index churn and allows reactivation without re-indexing.

Hard deletes (`users.id` removed) are handled by `ON DELETE CASCADE`.

### 5.4 How Tier 1 and Tier 2 combine

- **Keyword only** → Tier 1 SQL query only
- **Free text only** → Tier 2 vector search only
- **Both** → Keyword filter first → semantic reranks survivors → `final_score = (keyword_score × KEYWORD_WEIGHT) + (semantic_score × SEMANTIC_WEIGHT)`

Score weights: `KEYWORD_WEIGHT = 0.6`, `SEMANTIC_WEIGHT = 0.4` — defined as named constants, single place to change.

**Fallback rule:** If `free_text` is set AND keyword filter survivors == 0 (structured filter was too tight), ignore the keyword filter and run pure semantic search over all active employees. Include `"fallback_used": true` in the response so the UI can show "no exact skill matches; showing semantic matches."

### 5.5 Scoring formulas

Both scores must be on the same [0, 1] scale before combining.

**keyword_score** — level-weighted match ratio:

```
keyword_score = Σ(min(emp_level_i, requested_min_level)) / Σ(requested_min_level)
```

Clipped to 1.0. An employee who exceeds the requested level scores 1.0 for that skill, not higher.

**semantic_score** — remapped cosine similarity:

```
semantic_score = (cosine_similarity + 1) / 2
```

This maps the raw cosine range [−1, 1] to [0, 1].

**Chunk aggregation per employee:** Take the top-3 chunks by similarity, compute their mean. This avoids over-rewarding one-hit wonders (max) and dilution from many weak matches (full mean).

**Worked example:**

- Admin searches: skill `Java` (min_level=3) + free_text `"banking experience"`
- Employee A: Java level=4, 3 matched chunks with cosine sims `[0.85, 0.72, 0.60]`
- `keyword_score = min(4,3)/3 = 1.0`
- `semantic_score = ((0.85+0.72+0.60)/3 + 1) / 2 = (0.723 + 1) / 2 = 0.862`
- `final_score = 1.0 × 0.6 + 0.862 × 0.4 = 0.945`

### 5.6 Embedding Pipeline

The embedding service runs the same pipeline for both index-time chunks and query-time free text: tokenize → ONNX inference → mean pooling (real tokens only, not padding) → L2 normalize → 384-dim vector. The query vector is then passed to pgvector using cosine distance (`<=>`).

**Verification checklist (implementation):**
- Embed the same string twice → cosine similarity must equal `1.0`. If not, normalization or determinism is broken.
- Cross-check ONNX output against `sentence-transformers` reference implementation. Must match within ~1e-5 per dimension.
- Round-trip through pgvector: insert one known embedding, query for it, similarity must be `1.0`. Catches wire-format bugs.

### 5.7 Preprocessing Pipeline (shared, index and query)

The same preprocessing steps apply identically to index-time chunks and query-time free text. Mismatch between the two is a silent correctness bug.

Steps applied in order:
- **Strip HTML** — CV/experience content may come from a rich-text editor; tags eat the token budget without semantic value.
- **Normalize whitespace** — collapses runs of spaces, tabs, newlines, zero-width chars.
- **Skip empty/sentinel values** — never embed `"null"`, `"undefined"`, `"None"`; skip the chunk entirely.
- **Token-aware truncation** — char-based estimates are unreliable; use the actual model tokenizer and prefer sentence-boundary cuts.

**Do NOT apply:**

| Anti-pattern | Why it hurts |
|---|---|
| Stop-word removal | Negations and prepositions change meaning. `"experience with banking"` ≠ `"experience banking"`. |
| Stemming / lemmatization | WordPiece tokenization already handles morphology. |
| Manual lowercasing | `all-MiniLM-L6-v2` is uncased — the tokenizer does this internally. |
| Punctuation stripping | Sentence boundaries help pooling. |
| Spell correction | Corrupts rare tokens (names, tech terms — `"Vue"` → `"Value"`). |

**Preprocessing version:** When preprocessing rules change, bump `preprocess_version` in `skills_search_index` and schedule a full rebuild. Existing rows with old rules will silently mismatch queries built under new rules.

| Vector DB | pgvector (PostgreSQL extension, no extra service) |
| Embedding model | all-MiniLM-L6-v2 (384 dims, 256-token `max_seq_length`, 150-token chunk target, CPU, swappable) |
| Embedding library | onnxruntime + tokenizers (~50 MB, not sentence_transformers ~1.5 GB) |
| Embedding runtime | Python FastAPI service (sub-module of main app); localhost-only, X-Internal-Token auth |
| Stack | Python/FastAPI throughout. |
| Index approximation | Exact cosine similarity (60 employees, instant). Add IVFFlat only if headcount exceeds ~500. |
| CV chunking | `cv_overview.introduction` primary; fallback to full chunking recipe on `cv.cv` if `introduction` is empty |
| chunk_text format | Natural-language prose with source-type prefix. Never embed JSON. |
| metadata column | Separate JSONB sidecar for structured facts (filtering, boosting, display). GIN indexed. |
| Token limit | 150-token chunk target, 20–25% overlap; model `max_seq_length` 256. Measured by actual tokenizer, not char estimates. |
| Chunking refresh | Delete-then-insert per `(employee_id, field_type)` — re-indexes all sources of that type; wrapped in transaction |
| chunk_index column | INT NOT NULL DEFAULT 0; UNIQUE constraint on `(employee_id, field_type, chunk_index)` |
| preprocess_version | SMALLINT column; bump when preprocessing rules change → triggers rebuild |
| Index freshness | Real-time async re-index on every save (non-blocking, fire-and-forget with error logging) |
| Orphan cleanup | `@AfterRemove` hooks on source entities delete matching index rows |
| Skill embedding | Skills table rows embedded as `field_type='skill'`; used for free-text → skill ID expansion |
| keyword_score | Level-weighted match ratio ∈ [0,1]: `Σ(min(emp_level, min_level)) / Σ(min_level)` clipped to 1.0 |
| semantic_score | `(cosine_similarity + 1) / 2` → ∈ [0,1] |
| Chunk aggregation | Top-3 mean per employee |
| Score weights | Named constants: KEYWORD_WEIGHT=0.6, SEMANTIC_WEIGHT=0.4 |
| Fallback rule | If keyword survivors == 0 AND free_text set → pure semantic, `fallback_used: true` in response |
| Task scope | DONE tasks only, assignees only (not createdBy) |
| Default min_level | 1 (excludes level 0 "declared but no proficiency") |
| Default active_only | true (inactive employees filtered at query time; index rows kept for reactivation) |
| Pagination | None — return all results (max 60); add if > 200 |
| Access control | Admin-only, required. Guard implemented from day one. |
| Search strategy | Keyword filter first → semantic rerank on survivors (with fallback rule above) |
| Result hydration | Single `IN (...)` query per related table — no N+1 |
| Bootstrapping | One-time `PUT /admin/skills-search/rebuild` at initial deploy (~10 s for 60 employees) |

## 10. OBSERVABILITY

For an internal tool at this scale, structured logs with `event_type` are sufficient. No full SRE-grade dashboards needed.

**Embedding service — log on each call:**
```json
{"event": "embed_request", "latency_ms": 12, "token_count": 84, "status": "ok"}
{"event": "embed_request", "latency_ms": 0,  "token_count": 0,  "status": "error", "error": "model not loaded"}
```

**Search endpoint — log on each request:**
```json
{"event": "skills_search", "tier": "hybrid", "keyword_survivors": 12,
 "final_results": 8, "fallback_used": false, "latency_ms": 87}
```

**Index lag — log on every background re-index attempt:**
```json
{"event": "reindex", "employee_id": 42, "field_type": "experience", "status": "ok",    "latency_ms": 34}
{"event": "reindex", "employee_id": 42, "field_type": "experience", "status": "error", "error": "embedding service unavailable"}
```

Track failed reindex count in application metrics to detect stale-index accumulation.

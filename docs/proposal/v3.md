# SKILLS SEMANTIC SEARCH MODULE — ARCHITECTURE & FUNCTIONAL REQUIREMENTS

---

## 1. PURPOSE & CONTEXT

OWT is a software company with around 60 employees. When staffing a new project, users currently have no efficient way to find the right people. They rely on memory or manually browsing profiles. This feature solves that: a single search lets the user find employees whose skills and experience match the project's requirements in seconds, not hours.

---

## 2. OBJECTIVE

Build a skills search feature that allows users to find employees whose skills match a project's requirements.

The feature is delivered as a single unified search endpoint that supports two complementary modes, usable independently or together:

- **Semantic (free-text) search** — vector similarity search over employee CVs, experience records, and training logs. This is RAG minus the Generation step: retrieve and rank, not generate. User can type a natural language query like `"React developer with e-commerce experience"` and get ranked results.
- **Structured filter search** — fast SQL queries over skill/proficiency tables. User can filter by skill, proficiency level, position, experience, and training records.

When both modes are used together, structured filters run first to narrow candidates, then semantic search reranks the survivors.

---

## 3. TECHNOLOGY DECISIONS

### 3.1 Vector Database: pgvector

The project already uses PostgreSQL. pgvector is a PostgreSQL extension — no additional infrastructure, no extra service to deploy or maintain.

Exact cosine similarity (no approximate index needed at 60 employees).

Alternatives considered and ruled out: Qdrant, Weaviate, Milvus, Chroma, LanceDB, Elasticsearch, Typesense — all require a separate service.

### 3.2 Embedding Model: all-MiniLM-L6-v2

- 384-dimension vectors
- Runs on CPU (no GPU required)
- Well-tested for semantic similarity tasks
- Hard token limit: 256 tokens (`max_seq_length`; model truncates beyond this). Chunking targets 150 tokens with 20–25% overlap.
- Can be swapped for a better model later without changing architecture.

### 3.3 Embedding Runtime: Python FastAPI service

The skills-search module is built entirely in Python/FastAPI. The embedding service runs as a sub-module of the same FastAPI application, not as a separate sidecar.

**Library choice: onnxruntime over sentence_transformers:**

- `sentence_transformers` pulls in PyTorch (~1.5 GB) as a dependency — disproportionate for CPU-only inference on a small dataset in a production internal app.
- Use `onnxruntime` + the ONNX export of all-MiniLM-L6-v2 instead (~50 MB) — lighter, faster cold start, no PyTorch in production.
- Trade-off: `onnxruntime` requires manually handling tokenization, padding, attention masks, and mean pooling. If implementation complexity becomes a blocker, `sentence_transformers` is the fallback; the rest of the architecture is unaffected.

**Security:** The `/embed` endpoint is internal — called only by the FastAPI search module. It must be protected with a shared secret header (`X-Internal-Token`) and bound to localhost or an internal network interface only.

## 4. ETL (Extract, Transform, Load)

The ETL pipeline extracts raw employee data, transforms it into text chunks, generates vector embeddings, and loads them into pgvector. It runs on initial load and incrementally as source data changes.

See [etl.md](etl.md) for the detailed specification: trigger conditions, source entities, and field mappings.

---

## 5. Query

The query layer handles incoming search requests from the user. It accepts a natural language query and/or structured filter parameters, converts the query text into a vector embedding, and retrieves ranked employee matches from the database. Structured filters narrow the candidate pool via SQL before vector similarity scoring is applied, ensuring results are both semantically relevant and structurally correct.

See [query.md](query.md) for the detailed specification.

### Integration options

The result experience can be integrated in one of three ways:

| Option | Description | When to choose |
|---|---|---|
| Existing chatbot | Add skills search as a chatbot capability. Users ask questions naturally and receive ranked employee results inside the chat flow. | Choose this if the main usage pattern is conversational Q&A, quick lookup, and follow-up questions. |
| New dedicated search page | Build a standalone skills search page with search input, filters, ranked results, evidence snippets, and shortlist actions. | Choose this if users need a focused staffing workflow with filtering, comparison, and repeated result review. |
| Both chatbot and search page | Expose the same backend search API to both the chatbot and a dedicated page. Chatbot handles natural-language discovery; the page handles structured review and actions. | Choose this if the feature should support both quick conversational lookup and a complete staffing workflow. |
